# ERPを真のSSoTとする場合の認定二次データ管理

## 概要

SSoT（Single Source of Truth / 信頼できる唯一の情報源）は、理想的には一つの正本データに全員が直接アクセスし、そこから参照・判断できる状態を指す。

ただし実務では、ERPなどの基幹システムが真のSSoTであっても、全利用者が直接アクセスできるとは限らない。その場合、多くの利用者にとって実際の参照元は、ERPからアクセス権を持つ者がエクスポートした二次データになる。

このとき、二次データを無秩序に扱うと、利用者が二次データをSSoTと誤認し、さらに三次データを作成することで、依存関係や業務フローが長大化し、収拾がつかなくなる。

本メモでは、ERPを真のSSoTとしながら、ERP由来の二次データをどのように管理すべきかを整理する。

---

## 前提

本件における前提は以下である。

- 真のSSoTはERPに存在する。
- ERPに直接アクセスできる人間は限定されている。
- 大多数の利用者はERPそのものではなく、ERPからエクスポートされた二次データを参照する。
- ERP raw exportは使い勝手が悪く、業務利用には一定の加工が必要である。
- 加工により、ERPとの完全一致性や正本性が曖昧になる。
- 利用者が二次データを正本と誤認すると、さらに三次データが増殖する。
- 三次データが増えると、どのデータが正しいか、どの業務判断に使われたか、誰が責任を持つかが不明確になる。

---

## 基本整理

本件では、データを次の4層に分けて扱う。

| 層 | 位置付け | 例 | 管理方針 |
|---|---|---|---|
| 1 | 真のSSoT | ERP本体 | 正本。最終判断・更新責任はこちらに置く |
| 2 | raw export | ERPから出力した未加工データ | 抽出時点の写し。加工前の証跡として保管する |
| 3 | 認定二次データ | raw exportを加工した配布用データ | 用途・抽出条件・加工条件・責任者を明示して管理する |
| 4 | 三次データ | 利用者が作成した個別集計・報告資料 | 個別用途の派生物。正本または共通参照元とは扱わない |

重要なのは、二次データをSSoTに昇格させないことである。

二次データは、あくまで「ERPを正本とする認定参照データ」であり、ERPそのものではない。

---

## 問題構造

典型的な失敗構造は次のとおりである。

```text
ERP
  ↓
一部の人が作成した二次データ
  ↓
利用者が二次データをSSoTと誤認
  ↓
各自が三次データを作成
  ↓
三次データ同士の差異が発生
  ↓
どれが正しいか分からなくなる
  ↓
照合・説明・再作成のコストが増大する
```

この状態では、ERPが正本であるという原則があっても、実務上は二次データや三次データが事実上の判断材料になる。その結果、正本との関係が見えなくなり、データ管理が破綻しやすくなる。

---

## 二次データ作成者を増やすべきか

ERPへのアクセス権を拡大し、二次データを作成できる人を増やすことにはメリットがある。

ただし、単純に自由化するのではなく、「認定された二次データ作成者」を増やす設計にするべきである。

### メリット

#### 1. ボトルネックを減らせる

ERPからデータを取得できる人が少なすぎると、依頼が一部の人に集中する。  
その結果、利用者は待てずに古いファイルや誰かの加工済みExcelを流用し、非公式な三次データが増える。

二次データ作成者を一定数に増やすことで、非公式コピーの増殖を抑えやすくなる。

#### 2. 業務意図に合ったデータを作成できる

二次データは、用途によって必要な形が異なる。

例:

- 営業管理用
- 在庫確認用
- 受注残確認用
- 月次報告用
- マスタ確認用
- CRM/ERP照合用

中央の管理者がすべての業務意図を理解して加工するのは難しい。  
業務を理解している担当者が、目的に応じた二次データを作れる状態には合理性がある。

#### 3. 責任の所在を明確化できる

「誰かが作った便利なExcel」ではなく、「この用途の二次データは、この担当者が、この抽出条件と加工条件で作成した」と定義できれば、責任分界が明確になる。

これは統制を弱めるのではなく、むしろ統制を強める方向である。

---

## アクセス権拡大の注意点

アクセス権を広げる場合、以下のリスクがある。

| リスク | 内容 |
|---|---|
| 抽出条件のばらつき | 同じ売上でも、日付条件・ステータス条件・対象範囲が異なる |
| 加工ロジックのばらつき | 除外条件、補正条件、集計単位が作成者ごとに異なる |
| 用語定義のばらつき | 「売上」「受注残」「見込」「有効案件」などの意味が揺れる |
| 古いデータの再利用 | 過去の抽出ファイルが最新版のように使われる |
| 責任の曖昧化 | 数値差異が出たときに、誰が説明すべきか不明になる |

そのため、アクセス権拡大は「自由化」ではなく「分権化」として設計する必要がある。

---

## 推奨する権限設計

ERP本体の更新権限と、ERPから参照用データを作成する権限は分ける。

### 許可しやすい権限

- ERPの閲覧
- 定型エクスポート
- 必要範囲の抽出
- raw exportの保管
- Power Queryやスクリプトによる再現可能な加工
- 認定二次データの作成

### 慎重に制限すべき権限

- ERP本体の更新
- マスタ修正
- 取引データの直接変更
- 権限設定変更
- 正本データの削除
- 公式マスタの無承認変更

正本を変更する権限と、正本から参照用データを作る権限は別物として扱う。

---

## 認定二次データ作成者制度

二次データ作成者は、誰でもよいわけではない。  
一定の条件を満たす担当者を「認定二次データ作成者」として定義する。

### 役割定義

| 役割 | 主な責任 |
|---|---|
| ERP管理者 | ERP本体、権限、正本データの最終管理 |
| データ管理者 | 二次データのルール、一覧、責任分界、用語定義を管理 |
| 認定二次データ作成者 | ERPから用途別の認定二次データを作成する |
| 利用者 | 認定二次データを参照し、必要に応じて個別用途の三次データを作る |
| 報告責任者 | どのデータを報告値として採用するかを判断する |

---

## 認定二次データに必要なメタ情報

認定二次データには、最低限以下を付与する。

| 項目 | 内容 |
|---|---|
| データ名 | 例: 受注残一覧、売上見込一覧、顧客マスタ確認表 |
| 用途 | 何の業務判断・確認に使うか |
| 作成責任者 | 誰が作成・説明責任を持つか |
| 抽出日時 | ERPからいつ抽出したか |
| ERP環境 | 本番、Sandboxなど |
| 抽出対象 | どの画面、テーブル、レポート、エンティティから抽出したか |
| 抽出条件 | ステータス、日付、部門、会社コードなど |
| 加工条件 | 列削除、列名変更、結合、除外、補助列追加など |
| raw export参照 | 元ファイル名、保存場所、抽出ログ |
| ERP由来列 | ERPの値をそのまま保持する列 |
| 加工列 | 計算・変換・判定により作成された列 |
| 更新頻度 | 日次、週次、月次、随時など |
| 注意書き | ERPが正本であり、このデータは参照用である旨 |

---

## 許容できる加工と避けるべき加工

### 許容しやすい加工

| 加工内容 | 理由 |
|---|---|
| 不要列の削除 | 値の意味を変えないため |
| 列順変更 | 値の意味を変えないため |
| 列名の日本語化 | 対応表があれば安全なため |
| 表示形式変更 | 値そのものを変えないため |
| コードへの名称付与 | 参照マスタが明確であれば許容できるため |
| 区分列の追加 | ロジックが明示されていれば許容できるため |
| 集計補助列の追加 | 計算式が明示されていれば許容できるため |

### 避けるべき加工

| 加工内容 | 理由 |
|---|---|
| ERP由来値の手修正 | 正本との乖離を生むため |
| ERP値の上書き | SSoT性を破壊するため |
| 根拠不明の除外 | 数字の説明ができなくなるため |
| 属人的な補正 | 再現性がなくなるため |
| 個人判断によるマスタ修正 | 正本責任を曖昧にするため |

修正が必要な場合は、二次データ側で直すのではなく、ERP側の修正依頼に戻す。

---

## 数値差異の扱い

数値がバラけること自体は、必ずしも悪ではない。  
問題は、なぜバラけているか説明できないことである。

### 悪いばらつき

```text
Aさんの売上表とBさんの売上表で数字が違う。
理由は不明。
どちらも「ERPから取った」と言っている。
```

これは統制不能な状態である。

### 許容できるばらつき

```text
A表は出荷日ベース。
B表は請求日ベース。
C表は未確定分を含む見込ベース。
それぞれ用途、抽出条件、加工条件、作成責任者が明記されている。
```

これは業務上必要な複数の見方であり、問題ではない。

目指すべきは、数字を常に一つにすることではない。  
数字の出どころ、定義、用途、責任者を説明できる状態にすることである。

---

## 三次データの扱い

三次データは、利用者が個別目的で作成する派生物である。  
三次データの作成自体を完全に禁止するのは現実的ではない。

ただし、三次データを正本または共通参照元として扱ってはいけない。

### 三次データに対する原則

- 個別用途の派生物として扱う。
- 全社共通の参照元にはしない。
- ERP由来データを修正した場合は、補正内容を明示する。
- 報告資料に使う場合は、元にした認定二次データを明記する。
- 他者へ再配布する場合は、認定二次データとの差分を明示する。

---

## 不一致発生時の確認順序

数値や内容に不一致が発生した場合は、次の順で確認する。

```text
1. ERP本体
2. raw export
3. 認定二次データ
4. 三次データ
5. 報告資料
```

原則として、ERPが最優先である。  
ただし、月次締め後の確定値や過去時点の報告値など、時点固定が重要なデータについては、その時点の確定データを別途管理する。

---

## 管理者が主体になるべき範囲

データ管理者が主体になるべき範囲は、すべてのデータ作成作業ではない。

主体になるべきなのは、データ生成と利用のルール設計である。

### 主体になるべき範囲

- ERPが真のSSoTであることの明文化
- 認定二次データの定義
- 認定二次データ作成者の条件定義
- 認定二次データ一覧の管理
- 抽出条件・加工条件の標準化
- データセットごとの責任者設定
- ERP由来列と加工列の区別
- 三次データを正本扱いしないルールの整備
- 不一致時の確認ルート整備
- 用語定義の管理

### 主体になりすぎるべきではない範囲

- すべての二次データ作成作業
- 全利用者のExcel修正
- 各部署固有の分析ロジックの保証
- すべての数値差異の個別調査
- 各担当者の判断責任の肩代わり
- 便利な表作成依頼の無制限な受け入れ

管理者の役割は、全データを作る人ではない。  
データ生成の交通整理をする人である。

---

## 実務上の推奨構成

```text
ERP
  ↓
raw export
  ↓
Power Query / スクリプト / 定型処理
  ↓
認定二次データ
  ↓
利用者の個別加工・報告資料
```

raw exportと認定二次データは両方残す。  
加工済みデータだけを残すと、後でERP由来の値なのか、加工後の値なのかが分からなくなるためである。

---

## 認定二次データの注意書き例

```text
本データはERPを正本とする参照用の認定二次データです。
ERP由来項目は抽出時点の値を保持していますが、列名変更、不要列削除、区分付与、集計補助列の追加を行っています。
ERPとの不一致が疑われる場合はERPを優先します。
本データを元に個別加工した三次データは、全社共通の正本または参照元とは扱いません。
```

---

## 社内ルール文言案

```text
ERPを真のSSoTとする。

ただし、ERPへの直接アクセスが限定されるため、業務利用上はERPから抽出・加工した認定二次データを参照用データとして配布する。

認定二次データは、用途、抽出条件、加工条件、作成責任者を明示する。

利用者が作成する三次データは個別用途の派生物であり、正本または全社共通の参照元とは扱わない。

数値差異が発生した場合は、ERP、raw export、認定二次データ、三次データの順に確認する。
```

---

## 結論

ERPを真のSSoTとする場合でも、全利用者がERPに直接アクセスできないのであれば、二次データの存在は避けられない。

そのため、二次データを禁止するのではなく、認定二次データとして管理する必要がある。

特に重要なのは以下である。

- ERPを真のSSoTとして明確化する。
- raw exportを抽出時点の写しとして保管する。
- 加工済みデータは認定二次データとして扱う。
- 認定二次データには用途、抽出条件、加工条件、責任者を明示する。
- 二次データ作成者は認定制で複数名に分散する。
- 数値差異は一律に誤りとせず、定義差・用途差として説明可能にする。
- 三次データは個別用途の派生物であり、正本扱いしない。
- 管理者は作業者ではなく、責任分界とルール設計の担当者になる。

この設計により、ERPのSSoT性を維持しつつ、現場が利用可能な二次データを安全に配布できる。
